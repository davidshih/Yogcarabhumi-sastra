目標。把 origin/codex/batch1-69（7 月的「可稽核翻譯管線」，9 個 commit，與 main 分岔 100 個 commit）合進 main：26 個衝突與 14 個「乾淨合併但其實不相容」的路徑，每一個都有明文裁決。正式排程器 scripts/runner.py、網站、譯稿一個 byte 都不變；分支的管線完整保留成獨立模組 scripts/audited.py；三個共用函式庫做真正的合併；再加上 owner 要的「只審不重譯」指令 audited.py audit。

Tier：hard。Security-sensitive：yes。Human approval：None。這個 run 不發布任何內容變更。跑完之後對卷 67–72 實際執行審查是另一個 PR（owner 已於 2026-10-13 核准範圍與做法）。

Goal and non-goals

Goals

  • G1　分支的東西都進 main。monorepo M2 只對 main 的一個 commit 拍快照，所以分支上的程式、prompt、測試必須在 main 上，而且測試要會過。
  • G2　每個衝突都有裁決。包含 git 沒報、但合起來會壞的路徑（見 Approach 的 Conflict ledger）。
  • G3　線上不退步。docs/、translations/、data/、scripts/runner.py、scripts/webapp.py、舊 prompt 與 main 的 44 個測試，bytes 與 dd46ba8 相同。合併這個 PR 之後 GitHub Pages 重新部署的內容與現在相同。
  • G4　舊譯文可以只審不重譯。新指令對已發布的卷跑「術語、義理」兩道附證據的審查與術語機械檢查；沒被點名的段落與所有段落 id 不動，被點名的段落交給 fixer 重寫後只重審那些段落；整卷不過時譯稿與網頁維持原狀。
  • G5　PR 合得進去。main 的 ruleset require-ci 要求名為 ci 的檢查，但 repo 沒有任何 CI workflow；這個 run 補上。

Non-goals

  • N1　不把兩支 runner 合成一支，也不把正式翻譯工作改成分支的 JSON 契約協定。那會改變每一個新翻譯工作的行為，需要另一個決定與另一個 run。
  • N2　不重新產生任何已發布的頁面，不套用分支的新 tooltip 顯示到既有頁面。
  • N3　不把 audited.py 推廣到 T1579 以外的論典（T1821 的術語表通不過分支較嚴格的 tooltip 驗證，見 Premises P9）。
  • N4　不在這個 run 裡對卷 67–72 執行審查。那要真的模型額度與數小時，由 orchestrator 在合併後另開 branch 與 PR 執行（見 Verification 的 After the run）。
  • N5　不改 scripts/webapp.py，不讓網頁介面操作 audited 工作。
  • N6　不處理 codex/auditable-translation-pipeline 的內容：它是 batch1-69 的較舊版本（只差 scripts/runner.py 與 tests/test_pipeline_audit.py，batch1-69 多 230 行、少 4 行）。Orchestrator 在最後的 commit 用 git merge -s ours 把它記為已被取代。

Approach

兩條管線並存，共用函式庫做真合併。分支不是 main 的另一個版本，而是從 689 行的共同祖先另外長出來的第二套管線，而且它的 base 比 main 舊（看不到 main 在 7 月上旬加的 80 個 commit）。所以：

  1. scripts/runner.py 維持 main 的 bytes。22 處衝突全部取 main。
  2. 分支的 scripts/runner.py 改名成 scripts/audited.py，加上 Contracts K4 列出的修改。它有自己的 job 資料夾與 prompt 資料夾，永遠不會認領正式排程器的工作。分支的 112 個測試改 import 這個模組。
  3. llm.py、build_translation_html.py、check_translation_coverage.py 兩支 runner 都要 import，做聯集（K1–K3）。
  4. 在 audited.py 上加舊譯文審查（K5）。

Difficulty tier

hard。三個共用函式庫的跨模組合併、一個「放錯就讓沒審過的文字上公開網站」的關卡、跨重啟的狀態，以及兩套測試的相容。

Security-sensitive

yes。

  • 模型輸出是不可信的輸入：它被當 JSON 解析、寫進 md、render 成公開網站的 HTML 與 search.json。Render 路徑的跳脫（html.escape）與 tooltip 屬性的組字要看。
  • Audit 資料（每次模型呼叫的 request、response、error）之後會 commit 進公開 repo。audit.redact_secrets 是唯一的遮罩；錯誤訊息可能帶環境資訊。
  • 新的 CLI（--resume <job id> 變成檔案路徑的一部分；--juans）與既有的 subprocess（codex exec、git）。
  • 新的 workflow：只有 contents: read，action 釘 SHA，run: 裡沒有 ${{ }}。

Human approval required

None。這個 run 不碰 auth、secrets、billing、資料刪除或 migration。合併 PR 會觸發 Pages 部署，但部署的內容與現在逐 byte 相同（acceptance 與 stage 5 都驗）。之後對卷 67–72 的審查會改動公開的譯文；它的範圍與做法 owner 已在 2026-10-13 核准，並以獨立的 PR 交付。

Risks and rollback

  • Rollback。合併後要退：git revert -m 1 <merge commit>。網站內容沒變，不需要重建任何頁面。
  • 共用函式庫的合併弄壞正式 runner。緩解：runner 本身 bytes 不變；44 個測試、81 頁重現、81 份譯稿的範圍檢查、claude limit 的檢查都是防護。codex 別名的分類是唯一刻意的行為改變。
  • CI 上的 Python 比本機舊（ubuntu-latest 是 3.12，本機 3.14）。Workflow 不裝 Python（多一個 action 就要多釘一個 SHA）。若 ci 因版本失敗，orchestrator 在 stage 5 處理（改寫不相容的語法，或加釘了 SHA 的 setup-python）。
  • 兩條管線有重複的小工具函式（atomic_write、flock、md_sections 等，約 300 行）。這是明知的債，等決定要不要合成一支 runner 時一起處理。
  • 正式的 llm.py 裡多了兩個只給測試用的 fake 後端。它們不在 FAKE_MODELS 裡，所以不會成為正式 runner 的 queue；echo 本來就是同性質的東西。
  • 審查對真的舊譯文可能很嚴，整卷不過。這是資訊不是故障：譯文維持原狀，報告列出原因。
  • 額度。卷 67–72 共 83 段，兩道審查約 166 次呼叫，加上 fix 與重審；與這個 pipeline 的 review 共用同一個 Codex 帳號。先跑最小的一卷量測。
  • 驗收測試是在沒有實作的情況下寫的。若 implementer 回報某個斷言與 K5–K7 矛盾，orchestrator 依「wrong oracle」程序判斷並重新上鎖。
