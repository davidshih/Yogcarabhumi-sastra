Plan v1 — per-juan translation progress page (MangaReader style)

Repo: ~/projects/translation/yogacara · Base: b703390 · Run folder: plans/20260929-progress-page/ · Planner: Opus 5.5

1. Goal and non-goals

Goal

  • Replace the placeholder docs/status.html (「翻譯進度」, linked from every page's rail footer) with a real progress page: for every work in works.json, one cell per 卷 (juan), each in exactly one of three states: 已翻 (done), 進行中 (active), 未開始 (todo).
  • Present it in the format of the user's iPhone app ~/projects/import firefox ios history/ios/MangaReader (「追更簿」): paper/ink palette with a vermilion accent, Mincho masthead with a screentone dot band, ink-outlined pill tab chips with counts, dashed hairline rules, one "series" block per work with a tilted round red stamp, and a chapter list per work (here: a grid of 卷 cells).
  • Done cells link to the existing 白話對照 page so the translated content is directly readable. Todo cells are greyed out and not clickable.
  • The page is regenerated automatically by the runner whenever it publishes status, so it stays current without manual steps.

Non-goals

  • No change to the iPhone app in this run (the user asked for the app too; that is a separate, later pipeline run in the other repo).
  • No redesign of other site pages, no change to docs/index.html, work index pages, or translation pages.
  • No live polling / JavaScript rendering. The page is static HTML generated in Python; filtering uses CSS only.
  • No change to the webapp (scripts/webapp.py), which has its own live job UI via /api/status.
  • No refactor of the duplicated rail markup in build_site_index / build_simple_work_index.

3. Approach

  1. Juan totals go into works.json as "juans": N (T1579 100, T1585 10, T1558 30, T1821 30 — the Taishō fascicle counts). If a work has no juans, the grid runs to the highest juan seen on disk or in an active job (0 → empty grid).
  2. States (per work, per juan 1..total):
    • 進行中 if the juan is in job["juans"] of a job in JOBS_DIR/*.json whose state is not in {"done","failed","cancelled"}, and that juan's progress[str(juan)] has no step of "done" or "cancelled" and no truthy cancelled key. A missing progress entry counts as active (queued job). The step string (or "queued" when absent) is kept for the tooltip.
    • else 已翻 if <docs>/<work>/translations/<work>-<NNN>-baihua.html exists (the readable page, not the Markdown source: a draft Markdown file exists mid-job, the HTML only after publishing).
    • else 未開始.
    Active wins over done (a re-translation in progress), but an active cell still links to its existing page.
  3. Where: a new build_status_page(jobs) in scripts/runner.py, called at the end of publish_status() with the jobs list it already loaded. Output path and docs root are both derived from STATUS_JSON.parent, never from ROOT, so tests that patch STATUS_JSON to a temp dir cannot overwrite the real page. Works come from WORKS_PATH.
  4. Look: keep the site rail (navigation stays consistent with every other page) and restyle only the content column as the 追更簿. CSS lives in docs/style.css under a new, scoped .progress-page section; the page links style.css?v=20260930 / theme.js?v=20260930 so browsers refetch the stylesheet.
  5. Filter: four visually hidden radio inputs + <label> chips; :checked ~ sibling selectors hide non-matching cells. No JavaScript.

Rejected alternatives

  • Client-side rendering from status.json (keep the current fetch pattern): the translated set is not in status.json, so it would need a new JSON manifest plus a JS renderer; more moving parts and untestable with the repo's stdlib tests.
  • A new standalone script (scripts/build_status_page.py): the page must be rebuilt whenever job state changes, and the only hook for that is publish_status() inside runner.py; the other page builders (build_site_index, build_simple_work_index) already live there.
  • "Done" = Markdown has any translated entry (juan_translated(), runner.py:625): true mid-job for partial drafts and requires parsing ~40 MB of Markdown on every save_job(). HTML existence is cheap and matches "readable".
  • Inline <style> in the page: would need doubled braces inside the Python f-string and would split the site's dark-mode convention across two places.
  • Keep meta refresh: it would reset the filter and scroll every N seconds; the static file only changes when the runner rewrites it anyway.

8. Risks and rollback

  • Hot path: build_status_page runs on every save_job(). Cost is one small JSON read, 4 globs and ~170 string pieces; negligible next to the LLM calls. It must not raise on odd job data (non-int juans, missing progress) — a crash here would fail job saves. Guard with the defensive parsing in §4.2; do not wrap it in a blanket except.
  • Test pollution: covered by deriving paths from STATUS_JSON and by the byte-identical check in the oracle.
  • CSS bleed: every new rule is scoped under .progress-page / .progress-* / .juan inside the status page; other pages don't use these classes.
  • Rollback: git revert the single commit; the old page is restored and the runner's extra call disappears with it.
