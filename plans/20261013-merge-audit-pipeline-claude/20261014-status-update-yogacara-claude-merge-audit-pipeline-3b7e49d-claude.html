6. 技術細節附錄

Root cause / evidence：diff review 的四個 finding

C-1 / G-1（high）換檔中途出錯，正式譯稿不見。第 9 步先 os.replace(md, backup) 再把候選稿 hard link 到原路徑；原本只接 FileExistsError，其他 OSError 會讓指令以 fail 收場但路徑是空的。修法：所有換檔都經過 settle_swap，路徑空就用 hard link 把搬走的檔放回去；候選稿已到位但沒記錄的，補記成 installed，之後失敗就會把原稿換回來；放不回去時保留紀錄、報告寫出檔案位置，下一次 --resume 再放。

C-2（high）重建後被殺再續跑失敗，網站停在候選稿。頁面與搜尋索引的快照原本只在記憶體（plan 自己就這樣寫，是 plan 的洞）。修法：快照存到 audits/<job>/backup/<n>-site/；任何一次失敗都還原譯稿與網站。隔了一次程序的還原不把舊索引寫回去，而是從譯稿重建，因為中間可能有別的工作發布了別卷。

C-3（medium）審查等待期間改了 policy，封存的版本跟實際審的不一致。修法：事件的 policy hash 在送出時取；過關前用重用規則把每一段再對一次（沒變就不呼叫模型，變了就重審那一段）；quality gate 存的就是這次對過的那一份；對的過程中又變就讓該卷 fail，--resume 會補完。

C3-1、C3-2（Codex，第二輪修正的重審）。候選稿拿不出來時，整份索引快照寫回去會把別卷剛發布的更新退回；釘住輸入的清單靠列目錄，漏掉的 prompt 會改讀 live 檔。第三輪的修法：只把這一卷的搜尋紀錄放回去；必要檔案按名稱釘住，釘住期間清單外的輸入直接擋下。

C4-1（Codex，第三輪的重審，medium）。見第 4 節，已知限制。

O-1（medium，自己重讀修正時抓到的）重試才過的審查不會被重用。審查答案第一次不合格、重試才過時，佐證指向的是重試那筆事件，它的 prompt hash 是重試信封的 hash，跟重用規則比對的原始 prompt 不同，所以永遠被當成沒審過：續跑會重問，而 C-3 新加的最後核對會讓每次執行都多問一次，還可能問出新的 finding。修法：事件多記一個原始 prompt 的 hash，重用規則兩個都認。

修正輪 1 的重審抓到的四個（都在修正輪 1 新加的程式上）。C2-1、C2-2（Codex，high）：為了「連不了 hard link 也要放回去」加的複製備援，清理時會刪掉不是自己建的檔，被殺在半路會留下半份譯稿、續跑把它當成 owner 的新稿。修法是把複製整個拿掉，放回譯稿只用 hard link（唯一既原子又不覆寫的步驟），並在搬動譯稿之前先探測檔案系統做不做得出 hard link。G2-1（Grok，high）：最後核對是前後各讀一次輸入比對，改了又改回去比不出來。修法是只讀一次並釘住，最後核對、其餘檢查與封存都用這一份 bytes。G2-2（Grok，medium）：候選稿拿不出來時還從譯稿重建搜尋索引，索引會出現沒過審的文字。修法是這種情況寫回快照。

每一輪的反例都先在丟棄式副本實跑確認為紅才裁決。最終的測試檔對著修正輪 1 的程式跑有 13 個紅；修正輪 1、2 的程式做了 34 個手工 mutant、第三輪 6 個，全部被測試殺掉。
